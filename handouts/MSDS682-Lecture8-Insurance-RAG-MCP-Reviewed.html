01
Decide

Architecture judgment

Make Kafka earn its seat

  • One consumer and light traffic: a direct path may be enough.
  • Independent consumers: publish once and evolve separately.
  • Bursts and replay: retain work without coupling source and processor.

Ask the sharp question

Why not call the embedding job directly?

Direct path

S3 → embedder

Good when one small team owns one consumer, traffic is light, and custom backfill is acceptable.

Event backbone

S3 → Kafka → consumers

Useful when the change is durable shared history for multiple independently operated jobs.

For one document per second and one consumer, Kafka may be overkill. Say this clearly.

Kafka's value in this project

Three reasons can justify the event backbone

01 · Fan-out

Many independent uses

Embedding, audit, fraud, structured extraction, and notifications consume the same change event.

02 · Buffering

Absorb a burst

Five thousand documents may arrive now while the embedding service processes one hundred per second.

03 · Replay

Reprocess retained history

A new embedding model, bug fix, or compliance rule can rebuild derived state without changing the source.

Strong criterion: durable shared history, independently evolving consumers, and repeatable processing matter together.

Choose the interaction model

Request–response, task distribution, and event history are different

NeedDefault shapeExample
A user waits for an immediate answerHTTP / RPC / streamed responseQuestion → MCP tool → answer
One asynchronous job must be completedTask queue or Kafka Share Groups where supportedProcess one document with one worker
One event supports many retained usesKafka topic + separate consumer groupsEmbedding + audit + fraud + analytics
If someone is waiting, start with request–response. Add a queue for asynchronous work and Kafka only when retained event history, independent consumers, or replay materially improves the system.

Message design

Heavy objects live in object storage; Kafka carries the change event

Teaching shortcut

Whole document in Kafka

Simple for tiny text files and low volume, but large payloads amplify network, replication, retention, and consumer fetch costs.

Production pattern

Stable object pointer

Store the file in S3. Publish bucket, object key, object version, checksum, and business metadata.

The pattern generalizes. PDF, image, audio, video, and model artifacts stay in object storage; the event says what changed and where it lives.
02
Write

Maintain knowledge

Turn document changes into current, versioned state

  • S3 stores bytes. Kafka stores the change history.
  • Consumers apply business semantics. Kafka does not update the vector database.
  • Versions beat arrival order. Duplicate and late notifications are expected.

The running example

An insurance company issues and changes policies continuously

Create

New policy

A customer receives a new contract.

Replace

Renewal

A new version supersedes the earlier policy.

Amend

Endorsement

A document supplements—not always replaces—the base contract.

Delete

Withdrawal

A document or access grant is removed.

Update behavior is a business contract. A policy may have one active base contract plus several active endorsements. Model the active document set explicitly; do not assume every new file replaces everything before it.

Write path overview

A committed document change should eventually produce one idempotent domain event

Policy systemCreate or amend a document
→
Stage S3 objectWrite a versioned object first
→
Metadata + outboxCommit document state and event intent
→
Kafka eventPublish through CDC or a reliable relay
→
ConsumersMaintain serving and audit state
S3 plus Kafka is a distributed dual write. Use an outbox/CDC path or a notification bridge with reconciliation so an uploaded object cannot remain silently orphaned and a committed policy change cannot remain unpublished.

S3 identity

Publish exact object identity—not a temporary download URL

Avoid as canonical identity

Presigned URL

It expires, carries temporary access, and makes replay depend on yesterday's credential.

Prefer

Bucket + key + version

The consumer authenticates with its own role and reads the exact S3 object version referenced by the event.

Versioning is not the same as regulatory immutability. S3 Versioning preserves addressable versions; use Object Lock, retention, or legal hold when a version must be protected from deletion.

How the Kafka event starts

Prefer a domain event; use S3 notifications as a lower-level trigger

Pattern A · recommended

Versioned object + metadata outbox

Write the object first. Then commit document metadata and an outbox row in one database transaction; CDC or a relay publishes the Kafka domain event.

Pattern B · storage event

S3 notification → bridge → Kafka

Useful for simpler ingestion, but the bridge must enrich the storage event with policy semantics such as REPLACE versus AMEND and run reconciliation for missed work.

S3 notifications are at-least-once and are not ordered. Deduplicate them; use the S3 sequencer only to compare events for the same object key, while the policy system’s business version remains authoritative.

Ordering

Partition order helps; source versions decide correctness

  1. Partition by policy_id.All changes for one policy are stored in one partition.
  2. Enable idempotence and compatible producer settings.With idempotence enabled and supported in-flight settings, retries preserve order for records written to the same partition.
  3. Check document_version in the consumer.A delayed source notification must never overwrite a newer active version.
Consumers read partition storage order—not the unknowable “birth order” of events outside Kafka. The source business version is still the final authority for stale-event rejection.

No new Kafka operations

The AI indexing path reuses the same four operations

Filter

Reject

Unsupported type, failed checksum, unauthorized source, or obsolete version.

Map

Transform

Parse, clean, chunk, embed, and attach metadata.

Aggregate

Measure

Indexing rate, error rate, freshness, cost, and chunks per document.

Join

Enrich

Join a document with policy status, authorization scope, or feedback.

One embedding call can look like a map. The complete system is stateful because versions, authorization, retries, and current activation matter.

P0 correctness

A new policy version must not leave the old answer active

Embeddings are mutable serving state keyed by business identity. Append-only indexing is not enough.

Safe update pattern

Stage new chunks, then commit the active document set

Do not assume a vector database can atomically switch many records. Keep authoritative active-document metadata in a transactional catalog or supported alias. REPLACE supersedes a document; AMEND may add an endorsement to the active set.

Replay

A new embedding model can rebuild derived state

Kafka replay

Read retained events again

Use a new consumer group or reset offsets, then write vectors under a new embedding version.

Backfill

Scan the source catalog

If Kafka retention no longer covers the history, rebuild from S3 inventory or a current-document metadata table.

Replay requires retained event records and retrievable source versions. Configure Kafka retention deliberately, preserve the referenced S3 versions, and use Object Lock where regulatory retention requires protection from deletion.

Read

Serving layer

Expose current knowledge through an authorized contract

  • RAG is a retrieval-and-generation application pattern.
  • MCP is a protocol for exposing tools and other capabilities.
  • The server—not the model—owns authorization scope.

The MCP server is the application boundary. It may retrieve, filter, transform, or compute bounded results; it must not expose raw database access. Letting customers use external AI clients also creates an explicit data-egress decision.

Separate the abstractions

An MCP tool may expose a RAG retriever. The same MCP protocol can also expose structured data, APIs, or bounded computations.

MCP tool contract

Expose one narrow capability, not a database tunnel

{
  "name": "search_policy",
  "description": "Search the caller's active insurance documents.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "question": { "type": "string" },
      "policy_id": { "type": "string" },
      "top_k": { "type": "integer", "maximum": 8 }
    },
    "required": ["question", "policy_id"]
  }
}
Input schema is not authorization. A valid policy_id is still rejected when the authenticated caller may not access it.

P0 security

The model may choose the question; it must not choose whose data it can read

Never trust a customer or policy ID supplied by the model. Authorization scope must come from validated server-side identity and policy. Only approved clients and models should receive sensitive policy text.

Choose the serving store

Structured current state and semantic documents need different read paths

Structured current state

Lookup or filtered table query

Policy status, premium, active version, latest claim status, or model metrics.

Use: an authoritative API or current-state table with deterministic filters.

Unstructured semantic knowledge

Vector retrieval

Coverage language, exclusions, endorsements, letters, and policy clauses.

Use: chunking, embeddings, vector search, and RAG.

Do not embed everything. Exact structured facts should usually stay exact and queryable.

04
Prove

Evidence and limits

Make freshness, correctness, security, and scope observable

  • Failures are part of the design. Duplicate, late, missing, partial, and unauthorized inputs are expected.
  • Measure both paths. Indexing freshness and retrieval quality are different.
  • Know when to remove Kafka. More infrastructure is not automatically better architecture.

Correctness checklist

Every boundary needs a failure policy

FailureRequired responseEvidence
Object exists but no domain eventOutbox/relay monitoring plus periodic reconciliationEvery READY document has a published event ID
Duplicate S3/Kafka eventDeduplicate by event_id; apply changes idempotentlyOne active document state, no duplicate chunks
Older version arrives lateCompare business version; reject stale overwriteActive catalog remains on the newest valid version
Object fetch failsRetry with backoff and limits; route terminal failure to DLQ/reviewError includes exact object identity and cause
Embedding partially failsKeep staged chunks inactive; retry or discard the staged versionPreviously active documents remain available
Unauthorized policy requestedReject before search; audit the attemptZero cross-tenant or cross-customer chunks returned
Document contains prompt-like instructionsTreat retrieved text as untrusted data; never let it change authorization or tool policyAdversarial-document tests do not trigger extra access or actions

Measure the product

Freshness, retrieval, authorization, and cost need separate metrics

Write freshness

Event → active

p50 / p95 time from document change to searchable active version.

Retrieval + grounding

Find and cite the right clause

Expected documents, recall@k, answer support, cited document ID/version, and a bounded human rubric.

Security

No data leakage

Unauthorized retrieval count must be zero; audit every denied call.

Operations

Latency and cost

Embedding cost, tool p95, failures, retries, tokens, and backlog age.

“The chatbot answered” is not an evaluation. Prove the event path and the AI output separately. In insurance, the assistant should cite the governing document version and escalate uncertainty; it is not the final coverage adjudicator.

Architecture restraint

Do not use Kafka when the direct path is already the right path

One function

Single consumer

Only one embedding job cares about each upload.

Low operational need

No retained event history

Custom S3 backfill is acceptable and ordering is not material.

Simple ownership

One team, one release

The uploader and processor change, scale, and fail together.

Good architecture is not the largest diagram. Use Kafka when decoupling and retained stream semantics materially improve the system.

Use this example in a proposal

A reviewable three-week project needs one complete path

  • Source: sample policies or deterministic document updates.
  • Object storage: bucket/key/version identity, retention, and reconciliation.
  • Contract: operation, policy key, version, checksum, timestamps.
  • Kafka: justify fan-out, buffering, replay, or keyed state.
  • Processor: idempotent staging plus an authoritative active-document catalog.
  • Serving: one bounded MCP search tool.
  • Authorization: mandatory server-side policy scope and approved data egress.
  • Evidence: freshness, retrieval test, failure case, and fallback.
Minimum scope: a base policy plus an endorsement or replacement, one successful update, one duplicate/late event test, one authorized query, one denied query, and one retry or replay demonstration.

Lecture 8 synthesis

Five ideas to remember

  1. Heavy objects belong in object storage; Kafka carries append-only change records under a defined retention policy.
  2. Kafka earns its seat through durable fan-out, buffering, replay, and keyed state—not through popularity.
  3. Consumers apply document semantics idempotently and commit the active document set safely.
  4. RAG is a retrieval pattern; MCP is an authorized capability interface.
  5. The chat reply is request–response; the retained background event path is where Kafka usually belongs.
Final framing: Kafka retains change records. Domain consumers maintain current state and evidence. Serving layers expose bounded, authorized state to applications and AI.
