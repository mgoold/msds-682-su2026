Which product Lecture 9: named tools, once the requirement is explicit
Do not start from a product name. Product features, pricing, and availability change; the requirement is what you can still reason about next year.

Ask before naming a tool

Five questions decide the owner

  1. State: must it remember anything between events?
  2. Time: do windows, event time, or late records change the answer?
  3. Scale: how much throughput, state, and operational load?
  4. Recovery: what happens after a crash or a replay?
  5. Ownership: who maintains it, and in which language?

Three owners

Choose the smallest owner that meets the contract

Hard part: a simple effect

Plain consumer

Validate, call an API, write a result. State and time needs are small and explicit.

Trap: "every Kafka message needs a stream processor."

Hard part: a maintained table

Stateful SQL engine

The current answer per key is the product, and the team already operates SQL.

Trap: "SQL removes the need to define state and recovery."

Hard part: time plus state

Embedded library

Waiting, joining, and late policy belong in typed application code with tests and one release owner.

Trap: "code is always more powerful than SQL."

Demo 07 sat in the third column: a quote waits for a delayed outcome, joins on trip_id, and publishes an evaluation. There is no universal winner, only a fit.
