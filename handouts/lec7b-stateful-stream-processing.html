Define correctness

A stateful operation must answer four questions

QuestionRequired decision
Which records match?Contract, key, and partition alignment
How long may a match wait?Clock, window, completion, or expiry rule
How is state recovered?Cleanup, checkpoint, changelog, or replay
What can go wrong?Late, missing, or duplicate input and delivery policy
Demo 07 answer: match on trip_id, wait for the complete bounded set, keep state in memory, and publish with at-least-once delivery.
01
Operations

Know what each operation does

  • Kafka stores and delivers events.
  • Filter and map usually process one record at a time.
  • Aggregate and join remember earlier records.

Kafka versus processor

Kafka stores events; your processor computes results

Kafka broker

Retain and deliver

Topics, partitions, offsets, replication, replay.

Processor

Compute and remember

Filter, transform, aggregate, join, classify, and emit.

Classroom scripts stay bounded for evidence; the production processor keeps polling as new records arrive.

For the final project, name the component that owns each computation. Do not describe Kafka itself as the filter, map, aggregate, join, or model.

Stateless operations

Filter and map usually process one record at a time

Filter · one in → zero or one out

Keep valid trip requests

Evaluate a predicate against one record: required fields, valid coordinates, or a business threshold.

Map · one in → one out

Reshape one contract

Extract fields, convert units, or enrich from a fixed lookup before emitting a new record.

They become stateful when they read changing history. A changing lookup table or earlier event adds state and failure policy.

Stateful operations

Aggregate remembers a value; join remembers an unmatched record

Aggregate · many → running result

Remember an accumulator

Group by key, update count or average, optionally bound by a window, then emit on update or close.

Join · two histories → one fact

Remember unmatched records

Correlate by key, apply a time or completion policy, emit a joined fact, then clean up state.

Demo 07 uses join: each quote waits in keyed state until the outcome with the same trip_id arrives.

Two views of changing data

A stream records changes; a table represents current state

Stream

Every event matters

trip-requested, fare-quoted, trip-completed. History is append-oriented.

Table

Latest value by key

trip_id → latest trip status. Later updates replace the current view.

Demo 07 treats quotes and outcomes as streams. Every quote and every outcome remains part of the evaluation history.

Two clocks

Event time says when it happened; processing time says when code saw it

ClockMeaningWhy it matters
Event timeTime recorded by the business eventWindows should reflect when the activity occurred
Processing timeTime the processor sees the recordNetwork delay and replay can move it later
Demo 07 is bounded by 8 expected pairs, not by event time. A production join must declare which clock and expiry policy govern its window.

Stateful joins

Implement the join explicitly

  • Store each unmatched quote or outcome by key.
  • Match records with the same trip_id.
  • Emit, expire, and recover under a declared policy.

Common misconception

Reading two topics is not a join

Subscribe

Receive both histories

The consumer sees quote records and outcome records.

Join

Implement correlation

Extract key, store unmatched input, match, compute, emit, and clean up.

Your code must define the join: store, match, compute, emit, and clean up.

Architecture decision

Do not split one route response into two topics just to create a join

DesignPipelineConsequence
A · BuiltOne route call → miles + minutes → quoteNo artificial join
B · RejectedSplit mileage + duration topics → join → quoteExtra topics, state, failure policy
The meaningful join is quote plus delayed outcome, not split route fields.

Lecture 7B synthesis

Design every stateful processor in four steps

  1. Define the input event and the required output event.
  2. Choose filter, map, aggregate, or join.
  3. Declare key, time bound, state, recovery, late-data, and delivery policy.
  4. Prove the path with an observable output and a failure case.
